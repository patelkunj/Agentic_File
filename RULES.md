# RULES.md — Workbase business rules

The canonical rule book. Code and tests reference these IDs. If a rule here is wrong, fix it here
first, then fix the code — never the other way round.

Every rule is enforced **server-side**. UI enforcement is a convenience, never the control.
`(schema: …)` names the column that holds the value, so nothing is hard-coded in code.

---

## A. Access and identity

**R-A1** An *employee* record exists for every person. A *user* is a login account linked to one
employee. Employees without a user are normal (`users.employee_id`).
**R-A2** A user has exactly one role (`users.role_id`). Roles: Admin, HR, Reporting Manager, Clerk,
Employee (`roles`).
**R-A3** Permission is per role × module × action, from `role_permissions`
(`can_view`, `can_edit`, `can_approve`, `can_override`, `can_delete`). Modules are the seven enum
values in that table. A role with no row for a module has no access to it.
**R-A4** The Admin role (`roles.is_admin = TRUE`) has every permission, always. Its matrix cannot be
edited, and the last Admin user cannot be disabled or demoted.
**R-A5** User status (`users.status`): `Invited` → `Active` on first successful login (sets
`password_hash`); `Locked` after 5 consecutive failed logins (`failed_login_count`);
`Disabled` by an Admin. Only `Active` users may sign in.
**R-A6** A successful login resets `failed_login_count` to 0 and sets `last_login_at`.
**R-A7** Unlocking a `Locked` account is an Admin action and is audited.
**R-A8** Disabling a user never deletes the employee record or any history.
**R-A9** Changing a role's permissions affects every user with that role immediately.
**R-A10** Employees may read and edit only their own personal data (R-E6); any cross-employee read
requires `can_view` on that module.

## B. Employee records

**R-E1** Identity fields — name, employee code, date of birth, gender, marital status, personal
phone, personal email — are employee-owned. Company email, department, position and salary are
company-owned and change only through employment records (§C).
**R-E2** Addresses (`employee_addresses`) are effective-dated with type `Current | Permanent |
Previous`. Adding a new Current address closes the previous Current one; earlier rows remain
visible. Nothing is deleted.
**R-E3** Maximum **2** emergency contacts per employee (enforced by trigger
`trg_emergency_contact_limit`; the service must return a clean error, not a raw SQL failure).
**R-E4** Documents (`employee_documents`) are uploaded by the employee with status `Pending`.
**Only Admin** may set `Approved` or `Rejected`; a rejection carries a reason.
**R-E5** Bank details are entered by the employee. The account number is **masked in every screen
and API response**; full values only in the secure export path, which is itself audited.
**R-E6** An employee may edit their own personal details, addresses, emergency contacts, bank
details and documents. Everything else about them is read-only to them.
**R-E7** A rejoining employee gets a new employee record linked to the previous one; tenure
calculations span both (R-J7).
**R-E8** Employee status (`employees.status`): `Active | Inactive | Resigned | Terminated |
Retired`. Only `Active` employees appear in approval queues, headcount and leave balances.

## C. Employment and job history

**R-J1** Employment terms live in `employment_records`, **append-only**. Saving a change creates a
new row; no past row is ever edited.
**R-J2** The new row's `effective_from` sets the previous row's `effective_to` to the day before.
The current row has `effective_to IS NULL`. Exactly one current row per employee.
**R-J3** Effective ranges for one employee never overlap and never leave a gap while employed.
**R-J4** Unchanged fields carry forward from the previous record. The UI shows a diff before saving.
**R-J5** Salary is **monthly, in INR** (`monthly_salary`). Display as `₹60,000 / month`.
**R-J6** Working hours: `net daily hours = end − start − (lunch_break_minutes + tea_break_minutes)`.
**R-J7** Employment type is derived: net daily hours **below 7** → `Part-Time`, otherwise
`Full-Time` (`employment_type_computed`). A manual `employment_type_override` requires
`override_reason` and is audited.
**R-J8** Saturday working status is **never set here**. It is read from the Saturday calendar
(§D) and shown read-only on the schedule.
**R-J9** A professional engagement (`is_professional_engagement`) is not salaried payroll: it
captures `tds_section`, `tds_rate_percent` and `pan_number`, deducted from each payment.
**R-J10** Position tenure = time in the current position; overall tenure = from the original join
date, spanning rejoins.

## D. Holidays, Saturdays and comp-off

**R-H1** A holiday has a name, date, type (`Mandatory | Optional | Restricted`) and a
recurring-yearly flag. `day_of_week` is generated by the database — never written by the app.
**R-H2** Applicability defaults to All and can be narrowed by work mode (`work_mode_scope`),
department (`holiday_department_scope`) or named individuals (`holiday_employee_overrides`).
**R-H3** **Resolution order** for one employee and date: individual override → department scope →
work-mode scope → default All. The first match wins.
**R-H4** **Mandatory** holidays are non-working for everyone in scope. **Optional** and
**Restricted (RH)** are working days unless the employee takes them, and taking one draws down the
employee's RH allowance.
**R-H5** A holiday falling on a **Sunday** is flagged in the list (it may justify comp-off).
Saturday is never auto-flagged — its status comes from R-H6.
**R-H6** `saturday_calendar` is the **single source of truth** for every Saturday: `Off` (behaves
exactly like a holiday) or `Working`, with the same scope and override tables as holidays and the
same resolution order.
**R-H7** A quick pattern (e.g. all Saturdays working, alternate Saturdays off) fills only Saturdays
that have not been edited manually (`pattern_source`), and never overwrites a manual entry.
**R-H8** Copy-previous-year clones names, types and applicability into the target year: fixed dates
shift automatically, festival dates must be reviewed, entries with the same name are skipped rather
than duplicated, and everything stays editable afterwards.
**R-H9** Comp-off (`comp_off_credits`) is credited by an Admin when an employee works a holiday or
an `Off` Saturday, recording source type, source date, hours worked and a note. Default credit is
1.0 day. Redemption links the credit to the leave application that used it (`redeemed`,
`redeemed_leave_application_id`).

## E. Leave

### Types and balances
**R-L1** Leave types are **CL**, **PL** and **LOP** only (`leave_types.code`). The code "CSL" is
wrong wherever it appears.
**R-L2** Type behaviour is data, not code: `is_paid`, `requires_balance`, `max_consecutive_days`
(CL = 2), `max_balance_cap` (PL = 45). LOP has no balance and no cap.
**R-L3** Balances are per employee, per type, per year:
`balance = opening_balance + earned − used`, capped at `max_balance_cap`. Balance never goes
negative for a type that requires balance.

### Applying
**R-L4** An application carries type, from/to dates, duration (`Full | First Half | Second Half`),
reason (required) and an optional attachment. Half day is only valid on a single-day request.
**R-L5** **Day count excludes** Sundays, `Off` Saturdays and applicable holidays inside the range
(§D). A half day counts 0.5.
**R-L6** The applicant sees current balance, this request and remaining-after-approval **before**
submitting; a result below zero is shown as a blocking warning.
**R-L7** **No automatic type splitting.** If the balance cannot cover the request, the system does
not silently convert part of it to LOP. The applicant changes the type, or the approver does at
review (R-L13). *(Decision D-06.)*
**R-L8** CL is capped at **2 consecutive days** (`max_consecutive_days`). A longer request may be
submitted but is flagged as requiring an override at approval (R-L14).
**R-L9** The application routes automatically to the approver derived from the current
`reporting_manager_id` (`leave_applications.approver_user_id`), and the applicant is shown who that
is before submitting.
**R-L10** A `Draft` is private to the applicant and enters the queue only when submitted.
**R-L11** HR may submit on behalf of an employee with no login; the audit records both the employee
and the actor.

### Approving
**R-L12** Admin may act on any request. HR and Reporting Managers act only where their role has
`can_approve` on `leave_approval`; `can_override` is a separate grant.
**R-L13** At review the approver may change the leave type (`final_leave_type_id`) and reduce the
days (`final_days`). Balance updates use the **final** values.
**R-L14** Approving a request that breaks a rule requires `is_override = TRUE`,
`override_rule_broken` and a non-empty `override_reason`, and is written to `leave_override_log`
with the approver and timestamp. Without a reason the approval is refused.
**R-L15** Rejection requires `rejection_reason`.
**R-L16** Approval updates `leave_balances.used` and writes `leave_approvals` and the audit rows in
**one transaction**. A failure anywhere rolls the whole thing back.
**R-L17** An approved or rejected application is terminal; changes happen through a new application.
*(Withdrawal/amendment is still an open question — PRD Q7.)*
**R-L18** An employee cannot approve their own request, including an Admin — a second Admin acts.

## F. Audit and data integrity

**R-D1** Every create, update and delete writes to `audit_change_log`: module, record type, record
id, field, old value, new value, actor, timestamp — in the same transaction as the change.
**R-D2** Logins, failed logins and account lock events write to `user_activity_log`.
**R-D3** Audit data is **read-only to everyone, including Admin**. No UI or API path updates or
deletes it.
**R-D4** Where an action is taken for someone else, the audit records both the subject and the actor
("on behalf of").
**R-D5** Deletes are soft wherever history matters (employees, employment records, leave
applications, holidays already used in a calculation).
**R-D6** Timestamps are stored in UTC and rendered in **IST**. Dates handled as calendar dates
(`DATE`) are never shifted by a timezone conversion.
**R-D7** Money is decimal, never float. Currency is **INR**.
**R-D8** Referential integrity is enforced by foreign keys; the app does not "clean up" orphans by
deleting parents.

## Rule-to-test map (start here when writing tests)

| Rule | Test |
|---|---|
| R-J1–R-J3 | Saving a salary change creates a second row; the first closes one day earlier; no overlap |
| R-J7 | 9:00–18:00 with 90 min breaks → 7.5 net → Full-Time; 8:00–13:00 with 30 min → 4.5 → Part-Time |
| R-H3, R-H6 | An employee with an individual override is off while their department works |
| R-L5 | A Mon–Fri range containing one mandatory holiday and one `Off` Saturday counts 4 days |
| R-L7 | 3 CL days with 1 CL remaining is refused, not split |
| R-L8, R-L14 | 3 consecutive CL days flags override; approval without a reason is refused |
| R-L13, R-L16 | Approving 2 of 3 requested days updates `used` by 2 and writes one audit set |
| R-L18 | An Admin cannot approve their own application |
| R-A3, R-A4 | HR without `can_approve` sees the queue, gets 403 on the action; Admin always passes |
| R-D1, R-D3 | Every mutation above produced audit rows; an update attempt on audit fails |
